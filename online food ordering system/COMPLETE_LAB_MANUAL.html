Introduction

Overview of MVC Architecture

The Model-View-Controller (MVC) is a software architectural pattern that separates an application into three interconnected components:

Component Responsibility Example
Model (M) Data and business logic, database interactions, validation MenuItem model handles menu item data
View (V) User interface presentation, display data, collect input HTML templates showing menu items
Controller (C) Request handling, coordinate Model and View MenuItemController handles CRUD
Benefits of MVC:
  • ✓ Separation of Concerns - Each component has distinct responsibility
  • ✓ Maintainability - Changes in one layer don't affect others
  • ✓ Testability - Components can be tested independently
  • ✓ Reusability - Models can be reused across different views
  • ✓ Parallel Development - Teams can work on different layers

Importance of RESTful Design

REST (Representational State Transfer) is an architectural style for designing networked applications.

Core REST Principles:

  1. Client-Server Architecture - Clear separation between client and server
  2. Statelessness CRITICAL - Server does not store client context
  3. Uniform Interface - Consistent API design with standard HTTP methods
  4. Resource-Based - Everything is a resource (menu items, orders)
  5. Idempotency CRITICAL - Multiple identical requests have same effect
Why REST Matters:
  • ✓ Scalability - Stateless design enables horizontal scaling
  • ✓ Simplicity - Standard HTTP methods are well-understood
  • ✓ Flexibility - Multiple client types (web, mobile, IoT)
  • ✓ Visibility - HTTP methods clearly indicate operation intent

Statelessness Principle

CRITICAL REQUIREMENT: The server does NOT store any client context between requests. Each request must contain ALL information needed to process it.
Approach Stateful (❌ WRONG) Stateless (✅ CORRECT)
Authentication Server-side sessions Token in Authorization header
User Context Stored in session Extracted from token
Scalability Limited (session affinity) Unlimited (any server)
Load Balancing Sticky sessions required Any server can handle request

Idempotency Analysis

HTTP Method Idempotent? Explanation
GET ✅ YES Reading data doesn't change state. Multiple calls return same data.
POST ❌ NO Creates new resource each time. Multiple calls create multiple resources.
PUT ✅ YES Replaces resource. Multiple calls with same data produce same final state.
DELETE ✅ YES First call deletes. Subsequent calls find nothing. Same final state.
PATCH ⚠️ DEPENDS Depends on implementation. May or may not be idempotent.

HTTP Status Codes

Code Name When to Use
200 OK Successful GET, PUT, DELETE
201 Created Successful POST (resource created)
400 Bad Request Invalid input, validation failed
401 Unauthorized Missing or invalid authentication
404 Not Found Resource doesn't exist
500 Internal Server Error Unexpected server error

URI Design Rules (STRICT ENFORCEMENT)

Rule ✅ CORRECT ❌ WRONG
1. Use Plural Nouns /api/menu-items /api/menu-item
2. NO Verbs GET /api/menu-items /api/getMenuItems
3. Use Hyphens /api/menu-items /api/menu_items
4. Lowercase Only /api/menu-items /api/MenuItems
5. No Trailing Slash /api/menu-items /api/menu-items/
6. Hierarchical /api/orders/5/items /api/order-items?order_id=5

Complete Endpoint List Example

Method URI Description Auth
GET /api/menu-items List all menu items No
GET /api/menu-items?category=main Filter by category No
GET /api/menu-items/{id} Get single item No
POST /api/menu-items Create new item Yes
PUT /api/menu-items/{id} Update item Yes
DELETE /api/menu-items/{id} Delete item Yes
GET /api/orders/{orderId}/items List items in order Yes
POST /api/orders/{orderId}/items Add item to order Yes
GET /api/customers/{id}/orders Get customer orders Yes
